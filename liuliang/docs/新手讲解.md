# 新手讲解：这个项目到底怎么回事

这份文档是给你自己看的。老师提问的时候，照着里面的说法讲就行。
不用背代码，把每块"在干什么、为什么这么干"说清楚就够了。

---

## 一、整体思路（30 秒能说完的版本）

整个项目就是一条流水线：

```
日志文件 → 解析成字典 → 统计 → 检测异常 → 画成图表 → 导出 CSV
```

一句话讲清楚：**日志原本是一行行文本，程序先把它变成结构化的数据，
然后数一数各种指标，再拿规则去比对找出可疑的，最后用图表展示出来。**

---

## 二、每个文件在干什么

| 文件 | 干什么 |
|---|---|
| `app.py` | 网站的"接待员"。前端点按钮发请求过来，它接住，然后去调 core 里的函数 |
| `core/parser.py` | 把一行日志文本拆成字典 |
| `core/statistics.py` | 数数：算趋势、Top10、各种分布 |
| `core/detector.py` | 查异常：按规则比对，找出可疑的 |
| `core/exporter.py` | 把结果写成 CSV |
| `config/rules.json` | 规则文件，改这里就能改检测行为 |
| `templates/index.html` | 页面长什么样 |
| `static/js/charts.js` | 图表怎么画 |
| `static/js/main.js` | 点按钮之后干什么 |
| `tools/generate_log.py` | 造演示日志用的 |

## 三、解析模块（parser.py）

### 为什么要用正则

日志长这样：

```
1.2.3.4 - - [10/Oct/2026:13:55:36 +0800] "GET /index.html HTTP/1.1" 200 2326 "-" "Mozilla/5.0"
```

要从中取出 IP、时间、URL、状态码。如果按空格切分会出问题，
因为时间里有空格、URL 里也可能有空格。所以要用正则表达式，
相当于写个模板去套。

### 关键的一行

```python
PATTERN_REQUEST = re.compile(
    r'^(?P<method>[A-Z]+)\s+(?P<path>.+?)\s+(?P<protocol>HTTP/[\d.]+)\s*$'
)
```

**老师可能会问：为什么 path 用 `.+?` 不用 `\S+`？**

答：因为攻击语句里经常带空格，比如
`GET /item?id=1 UNION SELECT password FROM users HTTP/1.1`。
如果用 `\S+`（不含空格的一串），只能截到 `/item?id=1`，
后面的 `UNION SELECT` 就丢了，检测就会漏报。
改成 `.+?` 再用末尾的 `HTTP/1.1` 来定位，就能完整取到整条 URL。
**这个是我实际跑测试时发现的一个 bug。**

### 输出的字典

```python
{"ip": "1.2.3.4", "time": ..., "method": "GET",
 "path": "/index.html", "status": 200, "size": 2326, "agent": "Mozilla/5.0"}
```

后面所有模块都只认这个字典，不用再碰原始文本。

## 四、统计模块（statistics.py）

### Counter 是什么

```python
from collections import Counter
ip_counter = Counter()
ip_counter["1.2.3.4"] += 1
```

Counter 就是个会自动计数的字典。给它一个列表，它直接告诉你每个元素出现了几次：

```python
Counter(["a", "b", "a"])   # 结果是 {"a": 2, "b": 1}
```

Top10 就是 `Counter(...).most_common(10)`，一行搞定。

### URL 为什么要归一化

`/user/1001`、`/user/1002`、`/user/1003` 其实是同一个页面。
如果不处理，Top10 URL 会被一堆 `/user/xxxx` 占满，看不出重点。

所以写了 `normalize_path()`，把纯数字换成 `{id}`，
这样它们就合并成 `/user/{id}` 一项了。

### 趋势图为什么会自动切换粒度

```python
span_days = (end - start).days
if span_days <= 2:
    按小时分组
else:
    按天分组
```

如果日志跨了一个月还按小时分，横轴会有七百多个点，图没法看。
所以跨度小用小时，跨度大用天。

还写了 `_fill_time_axis()` 补齐时间轴：
如果 10 点和 12 点有访问、11 点没有，也要把 11 点列出来填 0，
不然折线图会直接从 10 点连到 12 点，看起来像 continuous 的。

## 五、检测模块（detector.py）

这是最有话说的一块，老师大概率会问。

### 为什么规则要写在 JSON 里

如果把攻击特征直接写死在代码里，加一条规则就要改代码、重启服务。
写在 `config/rules.json` 里，改完文件下次分析就生效。

这叫"逻辑和知识分离"——代码负责怎么匹配，规则文件负责匹配什么。

### 六类检测分别是什么

**1. 高频 IP（HF-IP）**
一个 IP 来了几千次 → 扫描器或撞密码。

**2. 突发访问（BURST-IP）**
这个稍微有点技术含量，老师可能会问。

**问：滑动窗口是什么？**

答：想象一个固定长度的窗口在时间轴上往右滑。
比如窗口是 60 秒，我让左边界和右边界都从第一个请求开始，
右边界不断往右移，每移一次就看看窗口里有几条请求；
如果发现左右两个请求的时间差超过 60 秒了，就把左边界也往右移。
这样窗口里始终是最多 60 秒内的请求，记录下窗口里最多装了几条，
就是"某 60 秒内的最大请求数"。

这么做是因为：有些扫描器总共请求不算多，但它是一秒十几个地砸过来，
光看总数抓不出来，得看密集程度。

**3. 错误率（ERR-4XX / 5XX / IP）**
- 全站 4xx 高：可能被批量扫描（扫不存在的页面全是 404）
- 全站 5xx 高：服务端出问题了
- 单 IP 错误率高：这个 IP 在乱撞

这里加了个 `per_ip_min_requests = 50` 的限制：
某个 IP 只访问 2 次全错了，错误率 100%，但那是噪声不是攻击，所以请求太少的 IP 不算。

**4. 可疑 UA（UA）**
扫描器会在 User-Agent 里自报家门，比如 `sqlmap/1.7`、`Nikto/2.5`。
空 UA 也可疑，正常浏览器不会不写 UA。

**5. 攻击特征（12 条规则）**
这是核心，建议重点准备。举几个例子：

| 规则 | 匹配什么 | 实际含义 |
|---|---|---|
| LFI-001 | `../../`、`..%2f` | 想通过 `../../etc/passwd` 读系统文件 |
| SQLI-001 | `UNION SELECT` | 用联合查询拖库 |
| SQLI-002 | `' or '1'='1`、`SLEEP(` | 布尔盲注、时间盲注 |
| CMDI-001 | `;cat`、`\|whoami` | 拼接系统命令执行 |
| LOG4J-001 | `${jndi:ldap://` | Log4j 漏洞利用 |
| SSRF-001 | `169.254.169.254` | 探测云主机内网元数据 |

**6. 异常方法（METHOD-*）**
正常网站就用 GET 和 POST。出现 PUT、DELETE、TRACE 就是在探测服务器开了什么功能。

### 两个 bug（一定要准备，这是加分项）

老师问"遇到过什么问题"，讲这两个特别合适，因为是真的踩过的坑。

**bug 1：SSRF 规则误报**

现象：检测出来 2600 多条 SSRF，一看全是正常用户。

原因：规则里要匹配内网 IP，其中有个模式是 `0.0.0.0`。
而正常 Chrome 的 UA 里有版本号 `Chrome/120.0.0.0`，
里面的 `0.0.0.0` 被当成内网 IP 了。

解决：给 IP 模式前面加个断言 `(?<![\d.])`，
意思是"前面不能是数字或小数点"，这样 `120.0.0.0` 里的就不会被匹配。
另外给规则加了 `scan_fields` 字段，SSRF 只扫 URL，不扫 UA。

**bug 2：带空格的 URL 被截断**

就是第三节说的那个。请求行用 `\S+` 匹配 URL，
遇到 `UNION SELECT` 这种带空格的注入语句会被截掉，导致漏报。
改成用协议结尾来定位就好了。

这两个都写了回归测试，以后再改规则如果又出问题，测试会直接报错。

## 六、导出模块（exporter.py）

**问：为什么要用 `utf-8-sig` 编码？**

答：因为直接用 utf-8 存 CSV，Excel 打开中文会乱码。
`utf-8-sig` 会在文件开头写个 BOM 标记，Excel 看到它就知道这是 utf-8，
显示就正常了。这是 Windows 上的常见问题。

## 七、后端（app.py）

用的是 Flask，很轻量。几个要点：

**会话缓存**：分析完的结果按 `session_id` 存在内存里。
点"导出 CSV"的时候，不用把日志再解析一遍，直接从内存里拿。
缺点是服务重启就没了，但对这个项目够用。

**上传限制**：
- 文件最大 100MB（`MAX_CONTENT_LENGTH`）
- 只收 `.log` `.txt` 这类后缀
- 存的时候文件名前面加随机数，防止重名覆盖

**为什么用 Flask 不用 FastAPI**：
这个场景就是上传文件、算完返回，同步处理够用，
而且 Flask 只装一个包，代码也少，适合这个工作量。

## 八、演示日志怎么造的

`tools/generate_log.py`，12000 行，构成是：

- 62% 正常流量，用三角分布模拟白天多晚上少
- 20% 高频扫描（1 个 IP 打了几千次）
- 6% 突发流量（60 秒内密集请求）
- 8% 定向攻击（注入、遍历、Log4Shell 等）
- 1.5% 异常请求方法
- 2.5% 的 5xx 故障时段

随机种子是固定的，所以每次生成的结果都一样，能复现。

## 九、老师可能问的问题，提前准备

**Q：为什么选 Python？**
Python 处理文本方便，正则、字典、Counter 这些用起来很顺手，
做数据统计类的东西比较合适。

**Q：一万行为什么不卡？**
解析是逐行读的，不是一次性把整个文件读进内存。
正则都提前编译好了（`re.compile`），不是每匹配一次编译一次。
实测 12000 行从解析到检测完一共 0.85 秒。

**Q：规则能不能加？**
能，在 `config/rules.json` 里加一条就行，写个 id、类型、正则、危害等级，
不用改代码，重新分析就生效。

**Q：误报怎么办？**
这是我重点处理的问题，讲了上面那两个 bug。
另外可以通过调阈值控制，比如高频 IP 的阈值默认 300 次，
如果发现误报多可以调高。

**Q：有什么不足？**
- 规则是纯正则匹配，遇到多层编码的变形载荷可能绕过去，
  可以加个解码预处理
- 结果存内存，重启就没了，可以存 SQLite
- 文件再大的话可以考虑分片或者多进程

## 十、演示流程（10 分钟）

1. 打开页面，点"加载演示日志"（或者直接访问 `?demo=1` 自动加载）
2. 讲概览卡片：12000 条请求、188 个 IP、错误率 35%
3. 讲趋势图：能看到访问量的时间分布
4. 讲异常告警：四个等级各有几条，重点讲 critical 的那几条
5. 打开"疑似攻击请求明细"，挑两条 SQL 注入讲：
   谁（IP）、什么时候、打了什么 URL、命中哪条规则
6. 点"导出全部 CSV"，说结果可以拿去进一步分析

时间够的话再提一下那两个 bug，老师一般会给印象分。
