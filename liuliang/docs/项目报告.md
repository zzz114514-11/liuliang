# 项目报告：网站访问日志可视化分析工具

项目名称：网站访问日志可视化分析工具开发
适用年级：大二
技术栈：Python Flask + HTML/JS + ECharts
项目周期：2 周

## 一、为什么要做这个

Web 访问日志是网站运维里最基本也最重要的数据来源。攻击者的扫描、暴力破解、SQL 注入尝试都会在日志里留下痕迹，但日志动辄几万行，用肉眼看根本看不过来。

这个项目就是做一个工具：把 Nginx/Apache 的访问日志导进去，自动解析、统计、检测异常，再用图表把结果画出来，让人一眼能看出自己的网站正在发生什么。

## 二、架构

```
浏览器                    Flask 后端
(ECharts 画图)  <------>  app.py
   上传/看结果            路由、会话、CSV 导出
                             |
                             v
                     core/ 下面的四个模块
                     parser      日志解析
                     statistics  统计分析
                     detector    异常检测（读 rules.json）
                     exporter    CSV 导出
```

前端只负责展示，所有计算都在后端。后端 core 包不依赖 Flask，能单独跑单元测试，这是刻意分开的。

模块职责：

parser.py   读日志文件，一行一行拆成结构化数据。支持 combined、common、json 三种格式，认不出来就记一行错误继续往下走。

statistics.py   拿解析好的数据算各种指标，趋势、Top10、分布之类。

detector.py   规则引擎。规则和代码是分开的，规则写在 config/rules.json，代码只负责按规则去匹配。

exporter.py   把检测结果写成 CSV。

几个当时做的选择：

用 Flask 没用 FastAPI。这个项目的场景就是上传文件、算完返回，同步模型够用，而且依赖少，只装一个包，代码量也小，比较适合这个项目的工作量。

解析用流式。边读边解析，不把整个文件读进内存。实测 12000 行从解析到检测完 0.76 秒。

规则外置。检测逻辑（代码）和检测知识（规则）分开，加规则改阈值都不用动代码，改完重新分析就生效。

ECharts 放本地。static/js/ 里放了一份，答辩的教室如果没网也能完整演示。

## 三、检测规则

### 行为类

| 检测项 | 规则 ID | 默认阈值 | 说明 |
|---|---|---|---|
| 单 IP 高频访问 | HF-IP | 超过 300 次 | 疑似扫描或爆破，会附上错误率和访问路径数 |
| 单 IP 短时突发 | BURST-IP | 60 秒内超过 60 次 | 用滑动窗口算，能定位到具体时间段 |
| 全局 4xx 错误率 | ERR-4XX | 超过 15% | 可能被批量扫描 |
| 全局 5xx 错误率 | ERR-5XX | 超过 5% | 服务端故障，要马上查 |
| 单 IP 错误率 | ERR-IP | 超过 50% 且请求数不少于 50 | 排除掉低频噪声 |
| 可疑 UA | UA-* | 33 种指纹 | sqlmap、nikto、masscan、空 UA 等 |
| 异常请求方法 | METHOD-* | 不是 GET/POST/HEAD | PUT、DELETE、TRACE 这类探测 |

滑动窗口那个是这么想的：光看一个 IP 总共访问了多少次不够，还得看它是不是集中在很短一段时间里，自动化工具通常就是这个特征。

### 攻击特征（12 条，要求是 5 条以上）

| 规则 ID | 类型 | 典型特征 | 等级 |
|---|---|---|---|
| LFI-001 | 路径遍历 | `../../`、`..%2f`、`..%5c` 各种编码变体 | critical |
| LFI-002 | 敏感文件探测 | `/etc/passwd`、`.env`、`.git/config`、`wp-config.php` | critical |
| SQLI-001 | UNION 注入 | `UNION SELECT`、`information_schema` | critical |
| SQLI-002 | 盲注、报错注入 | `' OR '1'='1`、`SLEEP()`、`EXTRACTVALUE` | critical |
| SQLI-003 | 注释、堆叠查询 | `--`、`xp_cmdshell`、十六进制编码 | high |
| XSS-001 | 跨站脚本 | `<script>`、`onerror=`、`javascript:` | high |
| CMDI-001 | 命令注入 | `;cat`、`|whoami`、`$(id)` | critical |
| RCE-001 | WebShell | `c99.php`、`shell.php`、`base64_decode` | critical |
| SCAN-001 | 后台入口探测 | `/admin`、`/phpmyadmin`、`/actuator` | medium |
| SSRF-001 | 内网探测 | `169.254.169.254`、`file://`、`gopher://` | high |
| LOG4J-001 | Log4Shell | `${jndi:ldap://` 及混淆变体 | critical |
| TRAV-001 | 编码绕过 | `%00`、`%c0%ae`、`%252e` | high |

每条规则命中后会记录：命中次数、来源 IP 分布、首次和末次时间、5 条原始日志样本，这些都能导到 CSV 里。

## 四、测试情况

### 单元测试

25 个用例，全部通过，跑一次 0.9 秒左右。

覆盖了三种日志格式的字段级校验、非法行的容错、URL 归一化、各项统计指标、以及各类攻击的检出。

### 性能

```
12000 行，解析加统计加检测一共 0.72 秒，发现 42 项异常
```

日志 12000 行 2.12MB，解析成功率 100%，满足任务书里一万行以上不卡顿的要求。

### 过程中修的两个 bug

这两个都是跑测试的时候才发现的，也说明了为什么要写测试。

第一个，SSRF 规则把正常浏览器误判了。规则里有匹配 `0.0.0.0` 这个内网地址的，而正常 Chrome 的 UA 里有 `Chrome/120.0.0.0`，版本号里的 `0.0.0.0` 被当成内网 IP 了，一下报了两千多条。修法是给 IP 那几个模式加上 `(?<![\d.])` 前置断言，要求前面不能是数字或点；另外给规则加了 scan_fields 字段，SSRF 只扫 URL 和 referer，不扫 UA。

第二个，带空格的 URL 被截断了。请求行原来用 `\S+` 匹配 URL，遇到 `GET /item?id=1 UNION SELECT x HTTP/1.1` 这种没编码空格的注入语句，只截到 `/item?id=1` 就停了，后面的注入语句根本没进检测，直接漏报。改成用协议结尾来锚定，写成 `(.+?)\s+(HTTP/[\d.]+)`。修完 SQL 注入那两条规则的命中数明显上来了。

这两个都留了回归用例，以后再改规则如果又出同样问题，测试会直接报错。

### 演示日志

tools/generate_log.py 生成，12000 行。构成是 62% 正常流量（用三角分布模拟白天多晚上少）、20% 高频扫描、6% 突发、8% 定向攻击、1.5% 异常方法、2.5% 的 5xx 故障时段。随机种子固定，所以每次生成的结果一样，方便复现。

## 六、个人总结

做下来最大的体会是数据结构要先定好。这个项目一共有三层数据结构：解析出来的 LogEntry、统计出的指标字典、检测出的 Finding，把这三个定清楚之后，后面每个模块写起来都很顺，前端拿数据也直接能用。如果一开始没定好，后面肯定要来回改。

正则这块练了不少。日志解析和攻击特征匹配都是正则密集的地方，学会了预编译、边界断言、忽略大小写这些。特别是边界断言，第二个 bug 就是靠它解决的。

误报治理比想象中重要。第一个 bug 让我意识到，规则能匹配上只是第一步，能不能只匹配该匹配的才是关键。报了两千多条假的，比漏报还麻烦，因为人根本看不过来。现在测试里专门留了回归用例盯着这个问题。

模块化解耦确实有用。core 包不依赖 Flask，前端出问题的时候后端测试照样能跑，定位问题快很多。

还有不足。规则是纯正则匹配，遇到多层编码的变形载荷可能绕过去，后面可以加个解码归一化的预处理。分析结果现在是存内存的，服务重启就没了，可以落个 SQLite 存历史。文件再大的话可以考虑分片或者多进程。

版本管理是全程用 Git 做的，功能一个一个提交，提交信息按模块加动作的格式写，最后有十几次提交。
